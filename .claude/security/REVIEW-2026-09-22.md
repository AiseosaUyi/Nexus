# Security Review — 2026-09-22

## Scope

Not a full audit. This review was triggered while verifying the Nexus Brain
MCP feature (`database/migrations/29`–`31`) against a local Supabase
instance: a bug found in one new, unshipped policy (`business_integrations`)
turned out to be a recurring pattern across several *already-applied*
historical migrations. Everything below was read and, where marked
"confirmed," directly exploit-tested against a local Postgres instance —
nothing here is inferred from code-reading alone without a note saying so.

## Executive summary

- **Root cause, one pattern, found in 8 tables across 6 migration files.** A
  Postgres RLS policy correlates to `business_members` via
  `bm.business_id = business_id` — the unqualified `business_id` silently
  binds to `business_members`'s own column instead of the policy's own
  table, because `business_members` has a column of that name and it's the
  innermost match. No ambiguity error; just a wrong bind. Net effect
  depends on which table:
  - **Cross-tenant leak/tamper** (bug resolves to a tautology, always true)
    when the policy is on a *different* table than `business_members`.
  - **Silent deny** (bug resolves to false via RLS's self-reference
    recursion guard) when the policy is *on* `business_members` itself —
    already found and correctly fixed once before, in
    `23_fix_business_members_rls.sql`.
- **Confirmed exploitable, cross-tenant, read AND write**, on
  `business_integrations` (migration 31 — unshipped, fixed before ever
  being applied). Directly proved: an outsider user (ADMIN of an unrelated
  workspace) could `SELECT` another tenant's row including the encrypted
  Gruve API key, and `UPDATE`/would-be-`DELETE` it.
- **Same shape confirmed present** (by direct source read, not yet
  independently exploit-tested per table beyond the fix/re-test below) in:
  `assets`, `calendar_entries`, `opportunities`, `platform_health`,
  `command_action_log` — all **already-applied historical migrations**
  (`06`, `07`, `26`) per this repo's own CLAUDE.md ("all migrations through
  N must be applied"). If that assertion is accurate, this is **live in
  production right now** for those five tables.
- **`business_members` itself is NOT vulnerable** — it has the
  same-looking bug in `03_business_members.sql`, but `23_fix_business_members_rls.sql`
  already replaced it with a correct `SECURITY DEFINER`-based fix (required
  because a self-referential correlated subquery on `business_members`
  hits Postgres's RLS recursion guard rather than just mis-binding).
  Confirmed: reusing the naive "qualify the column" fix on `business_members`
  throws `infinite recursion detected in policy for relation business_members`
  and breaks every other table's policy that subqueries it. `23` must not
  be touched.
- **Exploitability does not depend on this app's own UI/code.** RLS is
  enforced by Postgres/PostgREST for *any* request bearing
  `NEXT_PUBLIC_SUPABASE_ANON_KEY` (public by definition — shipped to every
  browser bundle) plus any signed-up user's own session JWT. A direct
  `POST`/`GET` to the project's PostgREST endpoint bypasses whatever care
  the Next.js app takes; RLS is the only real control here.

## Findings

### F1 · `business_integrations` cross-tenant read/write · Critical · **Confirmed**
- **Asset at risk:** the encrypted Gruve API key (`secret_enc`) and
  integration config (`config`, e.g. `baseUrl`) for every workspace.
- **File:line:** `database/migrations/31_integrations.sql:36-57` (as
  originally written — already fixed in this same file, see Fix below;
  never applied to a real database).
- **Description:** `using (exists (select 1 from business_members bm where bm.business_id = business_id and bm.user_id = auth.uid()))` on all four policies (select/insert/update/delete). The unqualified `business_id` binds to `bm.business_id`, collapsing every policy to "is the caller a member (or ADMIN) of *some* business."
- **Attack scenario:** any user signs up for a free account (auto-becomes ADMIN of their own trivial workspace via `handle_new_business()`), then calls Supabase's PostgREST endpoint directly (`GET .../rest/v1/business_integrations`) with their own session JWT — no app UI involved. They see every tenant's integration row. As ADMIN of their own workspace, they also satisfy the INSERT/UPDATE/DELETE `WITH CHECK`/`USING` clauses for *any* `business_id`, letting them overwrite or delete another tenant's Gruve key.
- **Confidence:** Confirmed — reproduced live: outsider SELECT returned the victim's `secret_enc`; outsider UPDATE (in a rolled-back transaction) successfully overwrote it.
- **Fix:** qualify the correlation: `bm.business_id = business_integrations.business_id` (all four policies). Applied directly in `31_integrations.sql` since this migration has never been applied anywhere real. Re-tested after the fix: outsider SELECT returns 0 rows, outsider UPDATE affects 0 rows, legitimate ADMIN's own row still reads fine.

### F2 · `assets`, `calendar_entries`, `opportunities`, `platform_health`, `command_action_log` cross-tenant read/write · Critical (if `06`/`07`/`26` are applied to prod, per CLAUDE.md's own claim) · **To-verify against the real database**
- **Asset at risk:** uploaded file metadata + storage paths (`assets`); calendar/content-plan entries (`calendar_entries`); inbound gig/opportunity text including scam scores and draft replies (`opportunities`); platform health scores (`platform_health`); an audit/action log (`command_action_log`) — all cross-tenant.
- **File:line:** `database/migrations/06_assets.sql:26-58`, `07_calendar_entries.sql:34-66`, `26_command_center.sql:92-144`.
- **Description:** identical bug shape to F1, in policies on five different tables, none of them self-referential (so no recursion — the naive qualified-column fix is correct and sufficient here, unlike `business_members`).
- **Attack scenario:** same as F1 — any signed-up user, direct PostgREST call, no app UI needed. SELECT reads every tenant's rows; EDITOR/ADMIN-gated INSERT/UPDATE/DELETE let a user with *any* workspace's EDITOR/ADMIN role write into *any other* tenant's rows for these tables.
- **Confidence:** Confirmed for the *pattern* (identical source-code shape, verified by direct read of all three files) and confirmed for the *mechanism* (F1's live proof demonstrates exactly how this bug shape behaves under RLS). Not independently re-exploited per table beyond re-verifying `memories`/`workspace_api_tokens`/`agent_sessions`/`business_integrations`/`business_members` post-fix (see Verification below) — a full independent proof for each of these five specific tables was not run separately, for time reasons; the mechanism is identical enough that I'm not treating that as meaningfully in doubt, but flagging it as not individually re-proven.
- **Fix:** `database/migrations/33_fix_business_scoped_rls_policies.sql` (new) — drops and recreates all affected policies on these five tables with the correlation qualified against each table's own name, following the exact precedent already set by `11_fix_nodes_rls.sql`. Has never been applied to a real database yet; needs to be applied by hand like every other migration in this repo.

### F3 · `businesses` SELECT policy never granted access to anyone · Functional/availability bug, not a leak · **Confirmed** (reported separately, already fixed — see prior session)
- Included here only for completeness of the "same bug family" narrative. `02_businesses.sql`'s SELECT policy has the mirror-image mistake — `bm.business_id = id` — where the unqualified `id` binds to `business_members.id` (its own PK) instead of `businesses.id`, making the policy always false. Fail-closed, not a leak: no one (not even a business's own owner) could read a `businesses` row via the RLS-bound client. Fixed in `database/migrations/32_fix_businesses_select_rls.sql`.

### F4 · `nexus_key_` static-token minting via workspace_api_tokens (new, unshipped) · High · **Fixed before shipping, not independently re-exploited**
- Same bug shape in `29_mcp_auth.sql`'s `workspace_api_tokens` policies (never applied to a real database). Beyond the generic cross-tenant read/write, this one is MCP-specific and severe: a direct PostgREST INSERT lets an attacker choose `token_hash` themselves (the hash of a plaintext token of their own choosing) for *any* `business_id`, then use that self-chosen plaintext as a working `nexus_key_` Bearer token against the deployed MCP server — full read/write of that tenant's memories/docs/calendar/Gruve data via the MCP auth layer itself, no need to compromise anything else.
- Fixed directly in `29_mcp_auth.sql` (qualified to `workspace_api_tokens.business_id`) since unshipped. Not independently re-exploit-tested (the general mechanism was already proven via F1); the policy diff and column qualification were verified by direct read.

## Verification performed

Applied the corrected `29`, `30`, `31` + new `32`, `33` to a local Supabase
instance (restoring `23_fix_business_members_rls.sql`'s correct
`business_members` state first, since an earlier draft of `33` mistakenly
also touched `business_members` and had to be reverted). Re-ran, all
passing:

1. Outsider `SELECT` on `business_integrations` → 0 rows (was: leaked the victim's row).
2. Outsider `UPDATE` on `business_integrations` (rolled back) → 0 rows affected (was: succeeded).
3. Outsider `SELECT` on `business_members` → only their own business's row (unaffected by this review's changes; already correct via migration 23).
4. Outsider `INSERT` into `business_members` claiming ADMIN of the victim's workspace (rolled back) → rejected with an explicit RLS violation (unaffected by this review's changes; already correct via migration 23).
5. Legitimate ADMIN can still read their own `business_members` row.
6. Legitimate ADMIN can still read their own `business_integrations` row.
7. Outsider `SELECT` scoped to the victim's `business_id` on `memories`, `workspace_api_tokens`, `agent_sessions` → 0 rows each.

## Prioritized remediation

1. **Apply migrations `32` and `33` to the real database** (by hand, per this repo's process — never assumed applied). This closes F1–F2 for real if `06`/`07`/`26`/`31` are indeed live as CLAUDE.md claims.
2. **Confirm, don't assume, that `06_assets.sql`, `07_calendar_entries.sql`, and `26_command_center.sql` are actually applied to the production database** before treating F2 as "was live" vs. "already caught." This review could not check the real database directly.
3. Consider a lightweight regression check (a Vitest or a one-off SQL script run against a disposable branch) that asserts, for every `business_members`-correlated RLS policy in the schema, that the correlation is properly qualified — this exact bug shape has now recurred three separate times (`nodes` in `11`, `business_members` in `23`, and this review's five tables) across this project's history, which suggests it's worth guarding against structurally rather than trusting careful authorship each time.

## What was NOT covered

- No broader audit of authentication, input validation, secrets management, headers/CORS, rate limiting, or dependency CVEs — this review is scoped entirely to the one RLS bug family that surfaced during MCP verification.
- The real production database was never queried or connected to during this review (per this project's own hard rule — migrations are only ever applied by hand by the project owner). Every "confirmed" claim above is against a local, disposable Supabase instance seeded for this purpose.
- F2's five tables were not independently exploit-tested one-by-one the way F1 was; confidence rests on identical source-code shape plus F1's proof of the underlying mechanism, not five separate live reproductions.
